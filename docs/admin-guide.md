# 管理员手册

面向店铺管理员的日常操作说明。所有命令仅对 `config.yaml` 中 `admin_ids` 列出的 Telegram 用户生效，请在 **Bot 私聊**中使用。

准备工作：

1. 管理员先私聊 Bot 发送 `/start`——否则收不到运维告警私信。
2. 输入 `/` 时会弹出命令菜单：普通用户只能看到用户命令，管理员的私聊里会额外列出本文全部管理命令。
3. 本文中的「用户编号」指 `/orders` 输出里的 `user_db_id`（系统内部编号），不是 Telegram 用户名或手机号。

## 商品管理

新同步的上游商品默认 **0 价、下架**，必须先定价再上架，买家才可见。

| 命令 | 说明 |
|---|---|
| `/products` | 列出全部商品（含下架）：编号、售价、币种、上架状态、SKU |
| `/price <商品ID> <售价> [币种]` | 定价，如 `/price 1 9.99 USD`；省略币种时保留原币种。定价**不自动上架** |
| `/rename <商品ID> <新名称>` | 修改商品显示名称（可含空格），如 `/rename 1 美国1GB·7天`；目录同步不会覆盖人工名称 |
| `/describe <商品ID> <描述>` | 修改商品描述（显示在目录正文与详情页），如 `/describe 1 美国TMO 100条短信+50分钟通话-30天`；同步不会覆盖 |
| `/currency <商品ID> <币种>` | 只改计价币种，不换算价格数值 |
| `/publish <商品ID>` | 上架。要求正售价；真实采购模式还要求商品有 SKU、上游套餐 ID 和明确业务类型 |
| `/unpublish <商品ID>` | 下架，停止新订单；已创建的订单继续按下单时快照处理 |

典型上架流程：

```
/products                → 找到要上架的商品编号
/rename 3 美国1GB·7天     → 可选：改成面向买家的名称
/describe 3 100条短信+50分钟通话-30天  → 可选：目录正文里名称下方的副标题
/price 3 12.5 USD        → 定价
/publish 3               → 上架
```

每次价格、币种、上下架变更都会与操作者 ID 一起记入 `product_events` 审计表。买家已看到确认页时若发生调价/改币种，下单前必须重新确认最新报价。

## 订单与收款

| 命令 | 说明 |
|---|---|
| `/orders [状态]` | 查看订单，可按状态过滤：`pending_payment` `paid` `delivered` `delivery_failed` `cancelled` `refunded` |
| `/query <订单号>` | 主动核单：查询支付状态、补履约；已发货订单会把交付资料重新私信给买家 |
| `/paid <订单号>` | 手动确认收款并推进履约（EPay 回调丢失/延迟时的兜底；不重置已付款订单） |
| `/cancel <订单号>` | 取消待支付订单 |
| `/refund <订单号>` | 人工退款：金额退到买家**同币种余额**并关单。仅限已付款且采购未提交、明确失败或已人工核对的订单；正在上游处理中的订单请先在 Commbitz 后台处理 |
| `/dispatch <订单号>` | 实体卡实际寄出后确认发货。确认付款（/paid）不等于确认发货，必须显式执行本命令 |

正常订单全自动流转（支付回调 → 采购 → 私信交付），无需干预。需要人工介入的场景：

- **回调丢失**：买家已付款但订单一直 `pending_payment` → `/query` 核单，确认已收款仍未推进再 `/paid`。
- **履约失败**：系统一般会自动退款到余额并关单（`refunded`）；个别需要人工判断的用 `/refund`。

## 采购异常（人工核对）

| 命令 | 说明 |
|---|---|
| `/purchases` | 列出需要人工处理的采购任务：`submission_unknown`（提交结果不明）和 `rejected`（被上游拒绝） |
| `/bind <订单号> <上游请求ID>` | 在 Commbitz 后台查到真实请求后人工绑定；系统会重新核验交付资料，确认货物属于该订单后才交付 |
| `/retry <订单号>` | 重试被上游拒绝的采购 |

收到 `manual_purchases` 告警时的处理入口就是 `/purchases`。原则：**先在 Commbitz 后台核实，再决定 `/bind` 或 `/refund`**——拿不准上游是否已扣款时不要重试或重复下单，避免双重采购。

## 钱包

| 命令 | 说明 |
|---|---|
| `/adjust <用户编号> <币种> <±金额> [备注]` | 人工调账，如 `/adjust 3 USD +5.00 赔付`；买家会收到私信通知；扣成负余额会被拒绝，所有调整留有流水 |

币种必须填写，不同币种的余额相互独立、不自动换算。

## 运维

| 命令 | 说明 |
|---|---|
| `/status` | 运行状态：数据库、webhook、后台任务、最近备份时间、告警收件人数 |
| `/ackalert <告警标识>` | 确认某条告警已处理，如 `/ackalert telegram_handler`；监控条件仍存在时会再次触发 |

告警处理节奏：

1. 收到告警私信 → 先 `/status` 看全局。
2. 按告警标识处理：`manual_purchases` 走 `/purchases`；`stalled_orders` 用 `/orders paid` 找到停滞订单排查；`worker_*` / `database` / `backup` 类到服务器看 `journalctl -u shop-bot`。
3. 处理完 `/ackalert <标识>`。未确认的活跃告警每 30 分钟会再提醒一次。

详细机制（告警去重、备份保留策略、恢复流程）见 [商品与运维](operations.md)。
