# 商品管理与运行维护

本页描述已实现的收尾功能。默认单进程运行；外部支付、Commbitz 真实扣款和 Telegram 公网链路仍须在部署后验收。

## 商品管理

管理员先在私聊中发送 `/start`，并将 Telegram 用户 ID 配入 `admin_ids`。

| 命令 | 行为 |
|---|---|
| `/products` | 列出商品编号、售价、币种、上架状态和 SKU，含下架商品 |
| `/price 1 9.99 USD` | 设置售价和币种；省略币种时保留该商品原币种 |
| `/currency 1 USD` | 只改计价币种，不换算价格数值 |
| `/publish 1` | 上架；要求正售价，真实采购模式还要求 SKU、上游套餐 ID 和明确业务类型 |
| `/unpublish 1` | 下架，停止新订单；已创建订单继续按订单快照处理 |
| `/status` | 检查数据库、工作任务、webhook、最近备份和告警收件人数 |
| `/ackalert telegram_handler` | 确认已处理的消息异常告警；仍存在的监控条件会再次触发 |

新同步商品仍为 USD、零价、下架。先定价，再逐个上架。同步不会覆盖人工名称（`/rename`）、售价、币种和上架状态。切换至真实供应商时，空库不会植入演示商品；已有测试库中的演示商品应在切换前下架。

每次人工修改名称、价格、币种或上下架状态，都与 `product_events` 中的前后值和操作者 ID 原子提交。买家看到确认页后若价格、币种发生变化，必须重新确认；创建订单的事务还会复核商品状态，避免并发下架/调价绕过确认。

## 健康检查

- `GET /healthz`：200 表示 HTTP 进程可响应。
- `GET /readyz`：数据库检查通过、webhook 注册完成、履约与监控任务有进度且备份任务存活时返回 200；未就绪、任务停止或检查超时时返回 503。
- 返回仅包含状态和布尔检查项，禁止缓存，不包含订单、路径、原始错误或密钥。
- 数据库检查默认最多等待 2 秒。后台工作任务意外退出会使主进程报错退出，systemd 按策略重启。
- 就绪检查不发起采购或支付，也不证明第三方供应商、银行收款或真实交付已完成验收。备份失败由告警和 `/status` 显示，不阻止其他订单服务继续运行。

```bash
curl --fail --max-time 5 https://bot.example.com/healthz
curl --fail --max-time 5 https://bot.example.com/readyz
```

部署时将 `/readyz` 接入服务器之外的可用性监控。进程未启动、主机断网或 Telegram 自身不可用时，进程内告警无法保证送达。

## 管理员告警

`operations.alerts_enabled: true` 时，发送到 `admin_ids` 中每位管理员的私聊；收件人必须先与 Bot 发起会话。没有收件人时启动日志会提示，`/status` 显示收件人数。

默认每 30 秒扫描：

- `submission_unknown`：采购结果不明，需人工核对。
- 付款后履约/退款超过 15 分钟未推进；正常等买家证件、等人工物流不计入此类告警。
- 已交付或已退款，但通知超过 5 分钟未送达。
- 履约恢复异常、商品目录同步异常、机器人消息处理异常。
- 后台任务退出/失去进度、数据库不可用、备份失败。

告警仅含类别、数量、订单编号和安全提示，不转发异常原文、证件、LPA、支付密钥。告警与每个收件人的发送结果保存在 SQLite：相同问题默认 30 分钟提醒一次，变化或恢复会再次通知；某个管理员发送失败会重试，不重发给已成功接收的其他管理员。发送成功但落库前进程中断时，可能再收到同一条提醒。

数据库故障时使用内存限频直接通知管理员；进程重启会重置该故障兜底的限频状态。所有告警发送失败也会记录安全日志。告警只是通知，不会自动重购、退款或改变业务订单。

## 自动备份

默认启动后立即备份一次，之后每 24 小时备份，保留本数据库最近 14 份成功快照。失败后一分钟重试，同时产生管理员告警。

```yaml
backup:
  enabled: true
  directory: backups
  interval_seconds: 86400
  keep: 14
  timeout_seconds: 120
```

相对目录基于数据库目录解析。例如 systemd 模板数据库为 `/var/lib/shop-bot/shop_bot.db`，默认备份位于 `/var/lib/shop-bot/backups/`。

使用 SQLite 在线备份接口和独立只读连接，包含 WAL 中已提交的数据；业务可继续处理订单。先写权限为 `0600` 的临时文件，再做完整性校验、刷盘、原子发布；只有成功后才清理同一数据库的过期快照。其他文件、其他数据库的快照、符号链接不参与保留清理。该备份也包含钱包、订单、告警、会话及证件链接，应按业务数据库管理权限。

手动执行一次（不启动机器人，不迁移源数据库）：

```bash
cd /opt/shop-bot
sudo -u shop-bot env SHOP_BOT_DATABASE_PATH=/var/lib/shop-bot/shop_bot.db .venv/bin/shop-bot-backup
```

配置文件采用自定义路径时，还需传入 `SHOP_BOT_CONFIG`。命令成功输出快照路径和 `integrity_check: ok`，失败返回非零退出码。备份目录可以配置到已挂载的备份磁盘；同机目录不能覆盖整机磁盘损坏，需要部署侧复制到独立存储。模板启用了 `ProtectSystem=strict`，改为其他目录时需同步设置 systemd 的 `ReadWritePaths` 并配置目录属主。

## 恢复与验收

1. 停止服务和收款入口，保存现有数据库及其 `-wal` / `-shm` 文件，选择正确时间的快照。
2. 用 SQLite `PRAGMA integrity_check` 检查所选快照，应只返回 `ok`；在独立目录打开副本，核验用户余额、交易流水、支付凭据、订单与采购记录。
3. 对账快照时间之后的支付网关交易和上游采购。补齐缺失证据、冻结结果不明的采购后，再允许自动履约；较早快照不能反映快照之后已经发生的扣款。
4. 在服务停止期间恢复数据库，处理旧 WAL/SHM，设置数据库文件属主及权限，再启动单个进程。
5. 检查 `/readyz`、`/status`、下一份备份及管理员通知，完成一笔授权范围内的业务验收。

本地回归覆盖 WAL 在线快照、未提交数据隔离、备份保留、失败清理、钱包/订单恢复和告警重试。Linux systemd、证书、远端备份以及实款联调在实际部署时验收。

## 图文交付升级注意事项

升级前备份数据库。无方案版本且仍待发送的通知，会重新发送同一份已核验资料；已完成的通知不批量重发。若旧版已把漏发订单误标为完成，请通过 `/query <订单号>` 补发；此操作不会重新采购。新版本的发送进度可跨重启保留，长 LPA 的独立文本也参与进度记录。
